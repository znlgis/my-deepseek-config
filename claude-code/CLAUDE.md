# CLAUDE.md — Claude Code × DeepSeek 项目记忆

> 本文件是 Claude Code 的项目级记忆（Memory）。放在项目根目录或 `~/.claude/CLAUDE.md`
> 作为全局记忆。核心通用规则见仓库根的 [`shared/RULES.md`](../shared/RULES.md)，
> 本文件只保留 Claude Code 专属要点与内嵌的关键纪律。

## 模型分工（DeepSeek 双模型）

Claude Code 通过 `ANTHROPIC_MODEL` / `ANTHROPIC_SMALL_FAST_MODEL` 支持主模型 + 轻量模型：

- **主模型（Pro）**：`deepseek-v4-pro` —— 规划、架构、根因分析、代码审查、重型实现。
- **轻量模型（Flash）**：`deepseek-v4-flash` —— 后台快速任务、标题生成、简单编辑、探索。

> `deepseek-v4-pro` / `deepseek-v4-flash` 为 DeepSeek 当前官方模型；旧别名 `deepseek-reasoner` / `deepseek-chat` 已并入并停用。

## 核心原则

1. **意图优先，先辨再动。** 区分字面请求与真实目标。「看一下 X」「解释 X」不是「改 X」。
   不确定时先确认，不要假设。用户没有明确要求实现时，不要直接改文件。

2. **最小改动，完整解决。** 做能完整解决问题的最小改动，不碰无关代码。
   一个完整、正确的方案优于一个花哨或宽泛的方案。

3. **先读后写，不猜代码。** 不凭记忆写代码——先打开文件读，用真实文件内容验证假设。
   不要自我推测代码的行为。

4. **独立任务并行。** 多个互不依赖的读取、搜索、获取操作同时发起，不要串行等待。

5. **未经请求不创建文件。** 不主动创建 README、文档、注释文件或任何新文件，
   除非用户明确要求。

6. **用操作系统语言回复用户。** zh-CN 系统用中文，en-US 系统用英文；
   除非用户明确要求，否则不强制英文。

7. **任务开始前明确停止条件。** 想清楚「完成」的可观察条件。一旦满足立即停止——
   不做额外的润色、重构或验证循环。解决问题优于追求形式。

## 多步任务纪律

任何 ≥2 步的任务：

1. 先用 `TodoWrite` 写有序待办清单。
2. 同一时刻只保留**一个**「进行中」状态的任务。
3. 每完成一项立即标记为「完成」——不批量标记。
4. 范围变化时及时更新清单。

跳过待办清单意味着进度不可见，任务容易半途而废。

## 反模式（严格禁止）

- **禁止万能文件。** 不创建 `utils.ts`、`helpers.ts`、`service.ts` 之类无意义的通用文件名——
  使用描述性的文件名。

- **禁止 emoji。** 代码和注释中不使用 emoji，除非用户明确要求。

- **禁止 AI 填充词。** 不在注释或解释中使用「simply」「obviously」「clearly」
  「moreover」「furthermore」等无实际信息的词语。

- **禁止空 catch。** `catch(e) {}` 不可接受。如果错误确实可以忽略，
  必须注释说明为什么可以忽略。

- **禁止无注释的 `@ts-ignore` / `@ts-expect-error`。** 必须附注释解释为什么需要压制类型检查，
  以及何时可以移除。

- **禁止注释掉的代码。** 死代码属于 git 历史（通过 revert / checkout 恢复），
  不属于源文件。提交前清理干净。

- **禁止空文档。** 不要创建无实际内容的 TODO 文件、占位 README 或模板文档。

## 代码风格

- **优先 `const` 而非 `let`。** 用三元表达式或提前返回替代变量重赋值。
- **尽可能避免 `else`。** 用提前返回来压平代码结构，减少嵌套层次。
- **优先函数式数组方法**（`map`、`filter`、`flatMap`、`reduce`）而非命令式 `for` 循环。
- **减少变量数量。** 如果一个值只用一次，直接内联到使用点，不需要命名变量。
- **避免不必要的解构。** 当解构名不增加清晰度时直接用 `obj.prop` 点号访问。
- **不用导入别名**（`import { foo as bar }`），除非解决真正的命名冲突。
- **不用通配符导入**（`import * as Foo`）——使用命名导入。
- **不要过早提取函数。** 只用一次的辅助函数不必提取——它们分散逻辑而不增加清晰度。
- **保持函数内聚。** 相关的逻辑放在一起，不要为了「整洁」而拆散。

## 注释纪律

- **注释解释 WHY，不解释 WHAT。** 如果读代码已经能看出做了什么，删除注释。
- **不写 AI 模板注释。** 不写 `// This function does X` 之类机器生成的废话。
- **不用无用 docstring。** 匹配项目既有的 docstring 惯例；
  如果项目不用 docstring，不要添加。
- **不保留调试注释。** 提交前删除 `// TODO: fix this`、`// FIXME`、`console.log` 等临时标记。

## 上下文与 Token 效率

- **引用路径，别贴整文件。** 指向 `src/app.ts:42`，不要把整个文件内容塞进提示词。
- **委派而非堆积。** 大文件交由子代理 / 探索读取，不要全部灌入主上下文。
- **积极压缩。** 一条探索线索结论清晰后即压缩上下文，不要带着全部原始探索内容继续。
- **快变库先检索。** 对于特定或高频变动的库 / API，不要凭记忆写代码——
  先查官方文档或 `references` 源验证 API 签名。

## 质量基线

- 匹配项目既有的代码风格、命名与约定。
- 验证改动可构建 / 通过既有检查，不破坏调用方。
- 汇报发现时引用具体位置（`file:line`）。
- 交付前从头到尾复读每个改动文件，自查是否有遗留的调试代码、未用变量、TODO 标记。

## 证据纪律

完成前必须产生至少一条可验证证据：

- 测试通过
- 构建成功
- Lint 检查干净
- `grep` 确认无破坏的调用方

**证据先于声明。** 如果无法产生证据，说明还未完成——陈述还缺什么以及什么阻碍了验证。

## 常见陷阱

- **把「解释」当成「实现」。** 用户说「这段代码干什么的」时，只需报告分析结果，不要动手改。
- **过度设计。** 用户要一个简单的改动时，不要重构整个模块——按最小改动原则来。
- **忽略 OS 语言。** 在中文 Windows 上用户期望中文回复，不要用英文。
- **忘记停止条件。** 完成了用户的实际需求就停，不要再做「顺便优化」——额外的修改可能引入新问题。

## Skills 能力

本配置自带以下 Skills，在对应任务中自动或按需激活：

| Skill | 触发条件 | 功能 |
|-------|---------|------|
| `code-review` | 审查 PR / diff / 分支 | 五维度代码审查（正确性/安全性/可维护性/性能/风格） |
| `conventional-commits` | 提交代码 / 写 commit message | Conventional Commits 规范 |
| `security-review` | 安全相关 diff / PR | 六项安全审计（注入/密钥/认证/数据暴露/依赖/不安全配置） |
| `verification-before-completion` | 任务完成前 | 强制验证流程（文件完整性/调用者检查/构建/测试/lint） |

## 权限基线（见 settings.json）

- 默认放行读写与安全 git / 构建 / 测试命令。
- `rm` / `git push` / `git reset` / `sudo` / `docker` 等破坏性命令设为 `ask`。
- `.env`、密钥、证书文件 `deny`，禁止读取。
