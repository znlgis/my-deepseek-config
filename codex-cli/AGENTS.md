# AGENTS.md — Codex CLI 项目记忆

> Codex CLI 会自动读取项目根目录（及 `~/.codex/`）的 `AGENTS.md` 作为指令
> （最大 32KB）。核心通用规则见 [`shared/RULES.md`](../shared/RULES.md)，
> 本文件保留可直接落地的精炼版规则与工作流约定。

## 核心原则

1. **先辨意图再动手。** 区分字面请求与真实目标。「看一下 X」/「解释 X」不是
   「改 X」。用户没有明确要求实现时，不直接改文件。
2. **做能完整解决问题的最小改动。** 不碰无关代码。完整正确优于宽泛聪明。
3. **先读后写。** 不猜代码行为——打开文件，用真实内容验证假设。
4. **并行处理独立工作。** 把多个独立的读取 / 搜索 / 检索合并一批，不串行。
5. **未经请求不创建文件。** 不主动创建 README、文档或任何新文件。
6. **明确停止条件。** 开始前想清楚「完成」的可观测标准。满足条件且改动验证通过后即停止，
   不做未请求的润色、追加重构或额外验证。
7. **用操作系统语言回复用户。** zh-CN 系统用中文，en-US 系统用英文；除非用户明确要求，
   不强制切换语言。

## 多步任务纪律

任何 >= 2 步的任务：
1. 先写有序待办清单。
2. 同一时刻只保留一个「进行中」。
3. 每完成一项立即标记完成（不批量）。
4. 范围变化时更新清单。

不写清单就开工等于进度不可见，容易留半截。

## 上下文与 Token 效率

- **引用路径，别贴整文件。** 指向 `src/app.ts:42`，不要把整个文件塞进提示词。
- **委派而非堆积。** 大文件交由子代理读取，不要全灌入主上下文。
- **并行独立读取。** 需要读 3+ 个互不依赖的文件时，一次性发起。
- **积极压缩。** 一条探索线索结论清晰后即压缩，从干净上下文开始实现。
- **快变库先检索。** 具体或高频变动的库 / API 不要凭记忆写，先查官方文档。

## 反模式（阻断）

以下行为无条件禁止：

- **不建万能文件。** 不创建 `utils.ts`、`helpers.ts`、`service.ts` 等文件名——
  用描述性文件名。
- **代码 / 注释不用 emoji，** 除非用户明确要求。
- **不用 AI 填充词。** 禁止 "simply"、"obviously"、"clearly"、"moreover"、
  "furthermore" 等词出现在注释或解释中。
- **不留空 catch 块**（`catch(e) {}`）。确实可忽略的错误需注释说明原因。
- **不用无注释的 `@ts-ignore` / `@ts-expect-error`。** 必须注释说明必要性和移除条件。
- **不留注释掉的代码。** 死代码属于 git 历史，不属于源文件。
- **未经请求不创建文件**（见核心原则第 5 条）。

## 代码风格（实现时）

- **优先 `const` 而非 `let`。** 用三元表达式或提前返回替代重赋值。
- **避免 `else`。** 用提前返回压平嵌套——减少认知负荷。
- **数据变换优先函数式。** 用 `flatMap`、`filter`、`map` 替代命令式 `for` 循环。
- **减少中间变量。** 只用一次的值就地内联，不创建命名变量。
- **不用不必要解构。** 解构不增强可读性时用 `obj.prop`。
- **不用导入别名**（`import { foo as bar }`），除非消解真实命名冲突。
- **不用通配导入**（`import * as Foo`），用命名导入。
- **不提前提取只用一次的函数。** 散落逻辑而不增加清晰度。

## 注释纪律

- 注释解释 WHY（为什么这样做），不解释 WHAT（代码在做什么）。
  如果读代码就能知道 WHAT，删除那条注释。
- 不写 AI 样板注释。
- 不留注释掉的代码。
- 匹配项目既有的 docstring 约定；项目不用 docstring 就不加。

## 提交前自检（证据纪律）

完成不等于声明——声明前必须有可验证证据：

1. **复读每个改动文件**，从头到尾扫描残留的调试输出、TODO 注释、不完整逻辑。
2. **确认未破坏调用方。** 搜索被修改函数 / 类型的引用。
3. **有测试则运行。** 没有则明确说明测试不可用。
4. **检查未用导入、变量、参数。**
5. **产出至少一项可验证证据：** 通过的测试、成功的构建、干净的 lint、或明确的手动验证记录。

证据先于断言。拿不出证据就等于没做完。

## 何时提问 vs 直接执行

仅在以下情况提问：

- 存在多种解释且影响 / 工作量差异显著；
- 关键上下文缺失（哪个文件、什么错误、什么范围）。

否则选最佳默认值，说明假设后继续。

> **理解**：[你的解释]
> **不确定**：[具体歧义]
> **选项**：1. [A] — [影响]  2. [B] — [影响]
> **建议**：[选择 + 理由]

## 沙箱与审批

默认 `workspace-write` + `on-request`：可写工作区，越权操作（网络、工作区外写入、
破坏性命令）时按需征求同意。

## 技能（Skills）

本目录 `.codex/skills/` 下提供四个可复用技能：

| 技能 | 用途 |
| --- | --- |
| `code-review` | 多维度代码审查，按 diff 规模缩放深度 |
| `conventional-commits` | 生成符合 Conventional Commits 规范的提交信息 |
| `security-review` | 审计安全漏洞，提供检查清单与报告格式 |
| `verification-before-completion` | 验证先于声明——确保完成前有证据 |

需要时在对话中提及技能名称即可触发。
