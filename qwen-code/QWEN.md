# QWEN.md — Qwen Code × DeepSeek 项目记忆

> Qwen Code 的上下文记忆文件，层级加载机制如下：
>
> 1. `~/.qwen/QWEN.md` — 全局记忆，影响所有项目。
> 2. `.qwen/QWEN.md` — 当前项目记忆（新版 Qwen Code 0.3.0+）。
> 3. `<project-root>/QWEN.md` — 项目根目录记忆（向后兼容，读取优先级最低）。
> 4. 父目录级联 — 若当前目录无 `QWEN.md`，向上查找父目录的 `QWEN.md`。
>
> 核心通用规则见 [`shared/RULES.md`](../shared/RULES.md)，本文件补充 Qwen Code 专属要点
> 与关键纪律。

## 模型分工（DeepSeek 双模型）

Qwen Code 通过 OpenAI 兼容端点接入 DeepSeek：

- **主模型（Pro）**：`deepseek-v4-pro` —— 规划、架构、根因分析、代码审查、重型实现。
- **轻量模型（Flash）**：`deepseek-v4-flash` —— 探索、检索、简单编辑、通用问答。

默认使用 `deepseek-v4-flash`，遇到复杂推理时切到 `deepseek-v4-pro`（用 `/model` 切换或改
`.env` 中的 `OPENAI_MODEL`）。

> `deepseek-v4-pro` / `deepseek-v4-flash` 为 DeepSeek 当前官方模型；旧别名 `deepseek-reasoner` / `deepseek-chat` 已并入并停用。

## 核心原则

1. **先辨意图再动手。** 区分字面请求与真实目标。「看一下 X」/「解释 X」不是「改 X」。
   用户未明确要求实现时不要直接改文件。
2. **做能完整解决问题的最小改动。** 不碰无关代码。完整正确优于宽泛聪明。
3. **先读后写。** 不猜代码行为——打开文件，用真实文件验证假设。
4. **并行处理独立工作。** 多个独立的读取/搜索/检索合并成一批，不串行。
5. **未经请求不创建文件。** 不主动创建 README、文档或任何新文件。
6. **明确停止条件。** 开始前确认「做完」的可观察条件；条件满足且验证通过即停止，
   不做超出请求范围的润色、重构或额外验证。
7. **语言跟随 OS。** 用操作系统当前语言回复用户。zh-CN 用中文，en-US 用英文。

## 约束

- **不引入新模型。** 仅 `deepseek-v4-flash` 与 `deepseek-v4-pro`。
- **不擅自新增依赖**，除非用户明确说明理由。
- **纯配置优先。** 优先改提示词/配置，而非引入新工具。

## 多步任务纪律

任何 ≥2 步的任务：先写有序待办清单；同一时刻只保留一个「进行中」；每完成一项立即
标记完成（不批量）；范围变化时更新清单。

## 上下文与 Token 效率

- **引用路径，别贴整文件。** 指向 `src/app.ts:42`，别把整个文件塞进提示词。
- **并行独立读取。** 需读 3 个以上互不依赖的文件时，一次性发起。
- **快变库先检索。** 对具体或高频变动的库/API，不凭记忆写代码，先查官方文档。
- **按任务大小选模型。** 搜索/查找/简单编辑 → Flash；推理/复杂决策/多步分析/实现 → Pro。
  边界情形先用 Flash，力不从心再升级。

## 何时提问 vs 直接执行

仅在「存在多种影响差异大的解释」或「关键上下文缺失」时提问。否则选最佳默认值，
说明假设后继续。提问格式：

> **理解**：[你的理解]
> **不确定**：[模糊点]
> **选项**：1. [A] — [后果]  2. [B] — [后果]
> **建议**：[选择 + 理由]

## 反模式（阻断）

- 不建 `utils.ts` / `helpers.ts` / `service.ts` 之类万能文件——用描述性文件名。
- 代码/注释中不用 emoji（除非用户明确要求）。
- 不用「simply」「obviously」「clearly」等 AI 填充词——中文亦同，不用「显然」「简单地说」。
- 不留空 catch 块（`catch(e) {}`）。若错误确实可忽略，必须注释说明原因。
- `@ts-ignore` / `@ts-expect-error` 必须附解释性注释，说明为何必要及何时可移除。
- 不留被注释掉的代码。死代码属于 git 历史，不属于源文件。
- 未经请求不创建文件。

## 代码风格（实现时）

- **优先 `const` 而非 `let`。** 用三元表达式或提前返回代替重赋值。
- **避免 `else`。** 用提前返回来压平代码结构，减少认知负担。
- **优先函数式数组方法**（`flatMap`、`filter`、`map`）而非命令式 `for` 循环做数据变换。
- **减少中间变量。** 只使用一次的值就地内联，不创建命名变量。
- **避免不必要的解构。** 解构出的名字不能比 `obj.prop` 更清晰时就用点号。
- **不用导入别名**（`import { foo as bar }`），除非解决真正的命名冲突。
- **不用通配导入**（`import * as Foo`）——用命名导入。
- **不提前提取只用一次的函数。** 把函数聚在一起，单次使用的辅助函数不要提前提取，
  它们散落逻辑而不增加清晰度。

## 注释纪律

- 注释解释 WHY，不解释 WHAT。读代码本身就能看懂做了什么的话，删掉注释。
- 不写 AI 样板注释。匹配项目既有的注释约定；项目不用 docstring 就不加。
- 不留注释掉的代码。死代码从 git 历史取，不留在源文件里。

## 质量基线

- 匹配项目既有风格、命名与约定。
- 注释只解释 WHY，且只在代码库已有注释处补充。
- 验证改动可构建/通过既有检查，不破坏调用方。
- 汇报发现时引用具体位置（`file:line`）。
- 每个公开函数/方法在提交前必须至少有一个调用方。禁止死代码。
- 交付前从头到尾复读每个改动文件，确认没有遗留调试打印、TODO 注释、未完成逻辑。

## 证据纪律

禁止无证据声明「完成」。汇报完成前，必须产出至少一项可验证证据：

- 通过的测试、成功的构建、干净的 lint 检查。
- 对每个改动文件的从头到尾复读，确认正确。
- grep 调用方结果，确认无破坏。
- 若没有自动化检查，明确说明做了什么人工验证及观察结果。

证据先于断言。无法产出证据即未完成——说明剩余工作及阻塞原因。

## 挑战用户

如果要求的做法明显有问题或违背既有模式，在动手前说明：

> 我注意到 [观察]。这可能导致 [问题]，因为 [原因]。
> 替代方案：[建议]。按原要求进行还是尝试替代方案？

## 技能（Skills）

本配置提供四个可复用的工作流技能（放在 `.qwen/skills/` 下），在 Qwen Code 中通过
`/skill <skill-name>` 触发：

| 技能                                | 用途                               |
| ----------------------------------- | ---------------------------------- |
| `code-review`                       | 多维度代码审查                     |
| `conventional-commits`              | Conventional Commits 规范提交信息   |
| `security-review`                   | 安全漏洞审查                       |
| `verification-before-completion`    | 完成前验证门禁                     |

## 提交前自检清单

1. 复读每个改动文件——扫描遗留的调试打印、TODO、未完成逻辑。
2. grep 调用方，确认未破坏接口。
3. 有测试则运行全部测试。
4. 清理未使用的导入、变量、参数。
5. 确认未新建非请求的文件。
